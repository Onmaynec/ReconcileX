# ReconcileX

ReconcileX — backend для сверки банковских выписок, платёжных реестров и внутренних операций. Не проводит реальные платежи и не подключается к банкам. Техническая постановка: PV-FIN-03, редакция 1.0.

**Текущий статус:** версия 0.8.0, Security & Deployment Hardening, инженерный backend; полная промышленная приёмка ещё не завершена. Полный акт приёмки по ТЗ не подписан; непроверенные требования перечислены в docs/STATUS.md.

## Состав

Python 3.12, FastAPI, SQLAlchemy, PostgreSQL 16, Alembic, отдельный worker, SILO (S3-совместимое хранилище), автоматические резервные копии и Docker Compose. HTTP JSON API документируется автоматически: http://127.0.0.1:8000/docs и /openapi.json.

Денежные суммы хранятся только как целые minor units. Сверка возможна внутри одного счёта, валюты и периода. Автоматическая сверка 1:1 не выбирает произвольную запись при двух одинаково подходящих кандидатах. Группы 1:n и n:1 создаются вручную. Для крупных групп требуется независимый контролёр.

## Локальный запуск

1. Скопируйте .env.example в .env и замените DB_PASSWORD, JWT_SECRET, S3_SECRET_KEY, DEMO_PASSWORD на свои уникальные длинные значения.
2. Выполните: docker compose up --build -d
3. Создайте тестовые справочники и пользователей: docker compose run --rm api python -m app.seed
4. По необходимости заполните 150000 строк через команду demo_import ниже, затем откройте http://127.0.0.1:8000/docs и вызовите POST /api/v1/auth/token с телом JSON: {"username":"operator","password":"пароль из DEMO_PASSWORD"}.
5. Скопируйте access_token в Authorize Swagger UI. Источники — GET /api/v1/sources; периоды — GET /api/v1/periods; профили — GET /api/v1/profiles?source_id=...; правила — GET /api/v1/rules?source_id=....

Демо-роли: operator, controller, analyst, admin, auditor. Все создаются с паролем DEMO_PASSWORD только на демонстрационном стенде. Не запускайте seed с общим паролем на рабочем сервере.

## Демонстрация

1. Оператор вызывает POST /api/v1/imports/preview, указывая source_id, profile_id, period_id, kind (external/internal) и CSV/XLSX.
2. POST /api/v1/imports/commit проводит валидный пакет атомарно; повтор файла SHA-256 по тому же источнику возвращает уже имеющийся batch.
3. POST /api/v1/reconciliation/run?period_id=... с заголовком Idempotency-Key ставит фоновое задание.
4. GET /api/v1/issues?source_id=...&period_id=... показывает неоднозначности.
5. Оператор формирует ручную группу через POST /api/v1/match-groups. Необходимы external_ids, internal_ids, rule_id, period_id, source_id, comment и Idempotency-Key. Большую группу утверждает другой пользователь, controller, через /approve с expected_version.
6. Контролёр вызывает POST /api/v1/periods/{id}/close. Закрытый отчёт /api/v1/reports/period/{id} читается из сохранённого финансового snapshot.

Пример: внутренние +1000,00 и комиссия −20,00 сверяются с внешними 980,00. Все числа внутри хранятся как 100000, −2000 и 98000.

## Разработка и тестирование

При наличии PostgreSQL и настроенной DATABASE_URL:

- python -m pip install -r requirements.txt
- alembic upgrade head
- python -m app.seed
- python -m pytest -q

В CI используется настоящий PostgreSQL 16, а не SQLite. Основные регрессии находятся в tests/test_acceptance.py.

Сгенерировать демонстрационные файлы без импорта: python scripts/generate_demo.py --rows 150000 --out demo-output.

Загрузить все шесть форматов (150000 синтетических записей) сразу в PostgreSQL и SILO (S3-совместимое хранилище) после создания тестовых справочников:

docker compose run --rm api python -m app.demo_import --rows 150000

Повтор команды с тем же количеством строк не должен менять финансовые записи или пакеты. Запуск с другим количеством строк после первой загрузки создаёт другие файлы и может конфликтовать с естественными ключами; для проверки другого набора используйте новый тестовый стенд. Генератор не содержит реальных персональных или банковских данных.

## Безопасность и эксплуатация

API доступен только на loopback хоста в локальном Compose. Для внешнего доступа нужен TLS-терминирующий reverse-proxy. Нельзя использовать значения секретов из .env.example. Пароли Argon2id; источник проверяется сервером на каждом маршруте чтения и изменения. PostgreSQL запрещает UPDATE/DELETE проведённых исходных records, batch и audit.

Инструкция по автоматическому резервированию и проверке восстановления приведена в docs/OPERATIONS.md. Статус реализации, включая непроверенные Must, указан в docs/STATUS.md. Архитектурные решения — docs/ADR.md. Таблица статуса требований — docs/STATUS.md.

## Обновление v0.2.0

Контейнер backup создаёт резервную копию при старте, затем ежедневно в 03:00 UTC (настраивается BACKUP_HOUR_UTC). Хранятся 7 завершённых архивов по умолчанию, все дампы и S3-объекты проверяются по SHA-256. Доступны команды:

~~~sh
docker compose run --rm backup once
docker compose run --rm backup verify
docker compose run --rm backup restore-check
docker compose run --rm backup status --max-age-hours 36
~~~

Restore-check восстанавливает данные только во временную PostgreSQL БД, проверяет финансовые суммы и ссылки на оригиналы и не удаляет рабочие записи. Backup volume расположен на той же машине: организуйте его копирование на независимый носитель.

Опциональный TLS reverse proxy включается командой docker compose -f compose.yaml -f compose.tls.yaml up --build -d после установки валидных сертификатов в certs/ и TRUSTED_HOSTS в .env. Подробности — docs/SECURITY.md.

Измерения производительности на синтетических массивах: python -m scripts.benchmark --external 80000 --internal 100000 --preview 20000 --trials 3 --output demo-output/performance.json. Сквозная нагрузочная приёмка автоматической сверки 180000 строк ещё не выполнена; см. docs/PERFORMANCE.md.

История изменений — CHANGELOG.md; точный статус требований — docs/STATUS.md.

## Обновление v0.3.0

Для одиночного правила с обязательным reference и допуском по сумме 0 worker использует индексированный поиск строк по дате и пакетные операции PostgreSQL. Обратная неоднозначность и независимое согласование крупных операций сохранены; остальные правила продолжают выполняться прежним алгоритмом.

Для полноценного нагрузочного испытания 180000 **синтетических** строк на изолированной тестовой PostgreSQL:

~~~sh
python -m scripts.e2e_benchmark --pairs 80000 --internal-extra 20000 --external-extra 0 --output demo-output/e2e-180k.json
~~~

Для замера p50/p95 нескольких независимых прогонов добавьте --runs 3; каждый прогон создаёт собственные синтетические записи, поэтому заранее проверьте диск. На GitHub можно запустить workflow «Full Reconciliation Benchmark» вручную в Actions, не загружая тестовыми данными основную БД. Протокол и ограничения — docs/PERFORMANCE.md. В обычном CI проверяется уменьшенный end-to-end набор.

## Обновление v0.4.0

В JWT добавлена версия сессии `ver`, привязанная к `users.token_epoch`. При смене/сбросе пароля и отключении пользователя версия повышается: все выданные ранее токены перестают проходить проверку на следующем запросе. Обновление существующей БД проводится миграцией Alembic `0004_session_epoch`.

Доступны новые API:

- `POST /api/v1/auth/change-password` — изменение собственного пароля после проверки текущего; отзывает старые сессии.
- `POST /api/v1/admin/users/{id}/reset-password` — сброс пароля администратором, без записи нового пароля в аудит.
- `POST /api/v1/admin/users/{id}/disable` и `/enable` — управление активностью пользователя; отключение немедленно отзывает сессии. Нельзя отключить свой администраторский аккаунт или последнего активного администратора.
- `POST /api/v1/admin/grants/revoke` — отзыв доступа пользователя к источнику; все новые запросы к финансовым данным этого источника становятся недоступны. Worker повторно блокирует и проверяет учётную запись и гранты до завершения финансовой транзакции.

Контролёр больше не может закрыть или повторно открыть период, если внутри него есть записи, отклонённые импорты, группы или задания по источникам, на которые ему не выдан доступ. Создание пересекающихся периодов сериализовано PostgreSQL advisory lock.

Проверки сценариев и ограничения — [docs/SECURITY.md](docs/SECURITY.md), статус промышленной приёмки — [docs/STATUS.md](docs/STATUS.md).

Дополнительно реализованы `POST /api/v1/auth/logout-all` (отзыв всех текущих JWT без смены пароля), `GET /api/v1/admin/users` (список аккаунтов без паролей/хешей, с пагинацией) и `GET /api/v1/admin/grants?user_id=UUID` (список выданных источников). Чтение административных списков разрешено только admin.

## Обновление v0.5.0 — Off-site Recovery

Добавлена **опциональная** репликация завершённых архивов PostgreSQL + исходных файлов SILO в отдельный S3-совместимый сервис. Для рабочих данных требуется независимое HTTPS-хранилище с отдельными ключами, шифрованием на сервере (AES256 или KMS), версионированием и политикой Object Lock. Передавать резервные копии в GitHub Actions или коммитить секреты запрещено. Встроенный профиль по умолчанию **выключен**.

Для включения заполните переменные `OFFSITE_S3_*` и `OFFSITE_MANIFEST_HMAC_KEY` в защищённом `.env` и запустите:

~~~sh
docker compose -f compose.yaml -f compose.offsite.yaml up --build -d
docker compose -f compose.yaml -f compose.offsite.yaml run --rm backup offsite-sync
docker compose -f compose.yaml -f compose.offsite.yaml run --rm backup offsite-verify
docker compose -f compose.yaml -f compose.offsite.yaml run --rm backup offsite-drill
~~~

Внешний манифест публикуется **последним** — только после передачи и повторной проверки SHA-256 всех объектов. Сам манифест защищён HMAC с отдельным секретом; его изменение обнаруживается даже при пересчёте обычного SHA-256. При ошибке отправки **не удаляются старые локальные снимки**. Новые команды: `offsite-sync`, `offsite-verify`, `offsite-drill`; `status` теперь также контролирует свежесть подтверждённой внешней копии. Можно включить HTTPS webhook `OFFSITE_ALERT_WEBHOOK_URL` с уведомлениями без финансовых данных.

`offsite-drill` загружает внешний снимок в новый временный каталог, выполняет проверку восстановления в **отдельной временной PostgreSQL-БД** и удаляет временную копию. Существующая рабочая база никогда не перезаписывается. Настоящий DR-прогон на другом сервере, воспроизведение исходников в новом bucket и измеренные RPO/RTO ещё не проведены: Issue #6 остаётся открытым. Инструкция: [docs/OPERATIONS.md](docs/OPERATIONS.md).

## Обновление v0.6.0 — Reconciliation Performance

Индексированный 1:1-движок теперь поддерживает **одиночное reference-aware правило с любым неотрицательным `tolerance_minor`**, а не только точное совпадение суммы. Для нулевого допуска индекс по датам сохранён, для положительного — используется сортировка по сумме в пределах (счёт, валюта, reference) и двоичный поиск диапазона в minor units. Проверка разрешённого окна дат остаётся обязательной.

Поиск кандидатов по обеим сторонам симметричен: если один внутренний платёж подходит двум внешним (или наоборот), система не угадывает пару, а создаёт `ambiguous`. Сопоставления вне суммы/даты запрещены. `MatchGroup.delta_minor`, `explanation.tolerance_minor` и запись аудита сохраняют **точные целочисленные расхождения**, а превышение риска по любой из сторон оставляет группу `proposed` до согласования другим пользователем. Запись групп, участников, исключений и аудита остаётся атомарной с пакетами по 500.

Бенчмарк `scripts/e2e_benchmark.py` теперь принимает `--tolerance-minor` и `--drift-minor`; внутри сценария проверяются суммы в БД и суммарная дельта каждой подтверждённой пары, повторный импорт, job, закрытие периода и SHA-256 snapshot. В CI добавлен второй сквозной сценарий **250 пар с допуском 5 и дельтой 3 minor units**. Для полного эксперимента доступны параметры ручного workflow «Full Reconciliation Benchmark» на Actions.

~~~sh
python -m scripts.e2e_benchmark --pairs 80000 --internal-extra 20000 --tolerance-minor 5 --drift-minor 3 --output demo-output/e2e-tolerant-180k.json
~~~

Команда предназначена только для одноразовой **тестовой** PostgreSQL-БД с синтетическими данными. Изменение кода не является подтверждением времени обработки на полном наборе 180000 строк; для сравнения одиночного и многоправильного профилей нужен отдельный прогон на документированном стенде. Подробнее — [docs/PERFORMANCE.md](docs/PERFORMANCE.md); Issue #2 остаётся открытым.

## v0.7.0 — Multi-Rule Engine

Переписан основной алгоритм автоматической 1:1-сверки. Вместо SQL-поиска возможных совпадений для каждой строки при нескольких правилах worker один раз загружает минимальные поля записей одного источника и строит **индексы по четырём типам запроса**: с обязательным reference / без него, с точной суммой / с допуском в minor units. Правила по-прежнему проверяются по приоритету: решение допускается только при единственном кандидате в **обоих направлениях**. Если на одном приоритете подходят разные записи — создаётся исключение `ambiguous`, не выполняется угадывание.

Все режимы используют пакетную вставку групп, участников и аудита по 500 в одной PostgreSQL-транзакции. При расхождении сумм сохраняется фактический `delta_minor`, а высокорисковые группы остаются `proposed` до согласования другим пользователем. Открытые исключения по принятым парам переводятся в `resolved`; повтор задания не создаёт дополнительные активные группы.

В `scripts.e2e_benchmark` добавлен `--rules-mode priority-fallback`: создаются два правила с разными приоритетами, первое точное, второе допускает указанную погрешность. Скрипт проверяет не только суммы и количество групп, но и выбранное правило каждой подтверждённой пары. Отдельный небольшой E2E-сценарий добавлен в CI; полный нагрузочный прогон необходимо запускать на отдельной тестовой БД:

~~~sh
python -m scripts.e2e_benchmark --pairs 80000 --internal-extra 20000 --tolerance-minor 5 --drift-minor 3 --rules-mode priority-fallback --output demo-output/multirule-180k.json
~~~

При `--drift-minor 3` точное правило не подходит, и сверка обязана выбрать правило меньшего приоритета с допуском 5 minor units. По умолчанию `--rules-mode single` сохраняет прежний тестовый сценарий. Даже после оптимизации скорость на разных данных, включая плотные значения одинаковых сумм и широкий `day_window`, требует отдельного измерения. См. [docs/PERFORMANCE.md](docs/PERFORMANCE.md), Issue #2.

## v0.8.0 — Security & Deployment Hardening

- Rate limiting входа на TLS reverse proxy: отдельная зона Nginx по реальному адресу подключения, 5 запросов в минуту и ограниченный burst; превышение возвращает HTTP 429.
- Приложение использует X-Real-IP только если TCP peer совпадает с явно разрешённым адресом reverse proxy. Любой forwarded header от прямого/неизвестного клиента игнорируется, поэтому подмена IP не позволяет обходить DB login throttle.
- Для TLS-профиля выделен статический адрес proxy и отдельный subnet backend. BACKEND_SUBNET, TLS_PROXY_IP и TRUSTED_PROXY_CIDRS должны соответствовать друг другу.
- Nginx добавляет HSTS, X-Frame-Options и Permissions-Policy, отключает server tokens, сохраняет TLS 1.2/1.3 и перезаписывает клиентские forwarding headers.
- В CI добавлены TLS smoke с временным сертификатом, проверка security headers и негативная проверка ограничения входа через reverse proxy.
- Добавлены тесты доверия к proxy, отказа от spoofed X-Real-IP, защиты конфигурации и обязательной аутентификации всех API-маршрутов.

Релиз не закрывает Issue #4 целиком: внешний secret manager, MFA/SSO, полный RBAC acceptance и параллельные security испытания на целевом стенде остаются отдельными задачами. См. docs/SECURITY.md и Issue #4.
