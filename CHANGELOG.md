# Changelog

## 0.8.0 — Security & Deployment Hardening

### Периметр и авторизация
- Добавлена проверка доверенного reverse proxy: приложение принимает X-Real-IP только от IP, входящего в TRUSTED_PROXY_CIDRS. Прямой клиент не может подменить адрес через forwarded headers.
- Login throttle по username + client IP теперь использует доверенный адрес клиента, а не общий адрес контейнера Nginx.
- TLS reverse proxy получил отдельный Nginx rate limit для /api/v1/auth/token: 5 запросов в минуту на IP, ограниченный burst и HTTP 429.
- В Compose закреплён статический IP TLS proxy; адрес подсети и trusted CIDR вынесены в конфигурацию.
- Добавлены X-Frame-Options, Permissions-Policy, server_tokens off; сохранены HSTS, nosniff, no-referrer и TLS 1.2/1.3.
- CI запускает TLS proxy с временным сертификатом, проверяет HTTPS health endpoint, защитные заголовки и отказ при превышении лимита входа.

### Регрессионные проверки
- Проверено игнорирование поддельного X-Real-IP от прямого и недоверенного peer.
- Проверено принятие forwarded IP только от явно закреплённого proxy.
- Проверены malformed forwarded header и ошибочный CIDR.
- Добавлен контрактный тест: все /api/v1/* маршруты, кроме endpoint выдачи токена, требуют current_user.
- Проверены admin inspection endpoints для всех четырёх неадминистративных ролей и успешный доступ admin.

### Ограничения
Issue #4 остаётся открытым: полная RBAC-матрица по всем операциям, внешний secret manager, MFA/SSO, формальный параллельный security acceptance и эксплуатационная проверка сертификатов в реальном домене требуют отдельной приёмки. Наличие TLS smoke с временным сертификатом не доказывает корректность production TLS-развёртывания.
### Совместимость
Миграций PostgreSQL нет. Для стандартного локального профиля дополнительных настроек не требуется. При изменении docker subnet необходимо синхронно изменить BACKEND_SUBNET, TLS_PROXY_IP и TRUSTED_PROXY_CIDRS.

## 0.7.0 — Multi-Rule Engine

### Сверка
- Убрана последовательность SQL-поисков кандидатов на каждую внешнюю запись для правил с несколькими приоритетами.
- Создан единый индексированный путь 1:1 по источнику с четырьмя видами индекса: reference/без reference и нулевой/ненулевой допуск.
- Приоритет правила определяется первым уровнем с подходящими кандидатами, а несколько разных кандидатов на одном уровне создают `ambiguous`. Повторные совпадения одной и той же записи по нескольким правилам одного приоритета не считаются неоднозначностью.
- Проверка симметричности пары, account/currency, окна дат и суммы сохраняется. Фактические значения `delta_minor` поступают в группу, explanation и аудит.
- Все группы, участники, исключения и аудиторские события пишутся пакетами по 500 в одной PostgreSQL-транзакции. Сохранены идемпотентность и независимое согласование рискованных групп.

### Тестирование
- Новые проверки 621 пары через три уровня правил, включая 500 точных, 120 с допуском и одно совпадение без reference, финансовые суммы и аудит.
- Отдельные негативные случаи прямой/обратной неоднозначности между правилами одного приоритета, границ дат и допуска, high-risk approval и повторного запуска.
- В тестах отслеживаются SQL-запросы диапазонного поиска кандидатов; алгоритм не вызывает такие запросы для каждой строки.
- Расширены E2E-бенчмарк и ручной Actions workflow сценарием `--rules-mode priority-fallback`; небольшой сквозной запуск включён в Backend CI.

### Ограничения
Проверки в CI используют синтетические данные, а полный сценарий 180000 строк, шесть форматов и конкурентная многопользовательская нагрузка ещё не подтверждены измерениями. Длительность и потребление памяти зависят от распределения реквизитов, допуска и окна дат. Issue #2 остаётся открытым; Issue #4 и #6 также не закрыты.

## 0.6.0 — Reconciliation Performance

### Сверка
- Расширен индексированный 1:1-алгоритм для одиночного reference-aware правила с ненулевым допуском по сумме (от 0 до максимума, заданного правилом).
- Для нулевого допуска по-прежнему используется индекс по дате; при положительном допуске суммы сортируются по ключу счёт/валюта/reference, затем бинарным поиском отбирается диапазон minor units и фильтруется дата.
- Проверка симметричной уникальности не позволяет выбирать одну из нескольких равнозначных пар, а для high-risk сохраняется независимое согласование.
- Утверждённые группы, аудит и объяснение содержат фактический целочисленный `delta_minor` и применённый допуск. Сохранена атомарная пакетная запись по 500 и повторный запуск без дублей.

### Бенчмарки и проверки
- E2E-бенчмарк получил режимы `--tolerance-minor` и `--drift-minor`; проверяются суммы по каждой стороне и агрегированная подтверждённая дельта.
- В обычном CI добавлен дополнительный E2E-прогон на 250 синтетических парах с допуском 5 и расхождением 3 minor units.
- Расширены интеграционные проверки на 620 пар, неоднозначность в обе стороны, границы суммы/даты, высокорисковое согласование, аудит и идемпотентность.
- Ручной «Full Reconciliation Benchmark» позволяет параметризовать допуск и расхождение при 80000 внешних и 100000 внутренних операциях.

### Открытые работы
Полная нагрузочная приёмка 180000 строк на выбранном оборудовании, 150000 строк шести форматов, p50/p95 при конкурентных запросах и оптимизация многоправильного движка требуют отдельных измерений. Issue #2 не закрыт. Production security #4 и независимый DR #6 остаются открытыми.

## 0.5.0 — Off-site Recovery

### Резервирование
- Добавлен опциональный внешний HTTPS S3 backup с SSE-AES256/SSE-KMS и HMAC-SHA256 манифестом.
- Манифест публикуется последним после read-back SHA-256 всех объектов; частичная копия не считается завершённой.
- Повторная передача пропускает уже проверенные объекты, не перезаписывает данные и не удаляет внешние архивы.
- Локальная ротация при ошибке внешней отправки запрещена; backup healthcheck включает свежесть внешней копии.
- Новые команды offsite-sync, offsite-verify, offsite-drill и опциональные HTTPS уведомления.
- Добавлен compose.offsite.yaml, документация восстановления, негативные тесты и CI-конфигурация.

### Ограничения
Реальный независимый S3, retention lock провайдера и катастрофоустойчивое восстановление на другом сервере пока не проверены. Issue #6 открыт.

## 0.4.0 — Security & Data Integrity

### Доступ и сессии
- JWT содержит `ver` и сверяется с серверным `User.token_epoch`, обеспечивая отзыв всех прежних сессий при смене/сбросе пароля и отключении пользователя.
- Добавлены самостоятельная смена пароля и выход со всех устройств, административный сброс пароля, блокировка и восстановление пользователя, отзыв SourceGrant.
- Для администратора добавлены списки пользователей и действующих грантов без хешей паролей. Все изменения аудируются без записи секретов.
- Запрещены отключение собственного администратора и отключение последнего активного admin.

### Финансовая безопасность
- Close/reopen теперь проверяет права контролёра на каждый задействованный источник периода, включая записи, исключения, группы и зафиксированные правила заданий.
- Worker блокирует и перепроверяет enabled, роль submitter и SourceGrant перед финансовым commit. Отозванные разрешения приводят к отказу без частичной записи.
- Конкурентное создание перекрывающихся периодов сериализовано через PostgreSQL advisory lock.

### Проверки
- Добавлены негативные E2E тесты на отзыв JWT, отключение пользователей, изменение паролей, source isolation, запреты на исходные файлы, повторное открытие и конкурентное создание периодов.
- Проверена миграция 0004 при переходе с базы v0.3 и на чистом стенде.

### Ограничения
Production TLS, внешнее управление секретами, полная многопользовательская security-приёмка и off-site DR пока остаются отдельными задачами. Issues #2, #4, #6 не закрываются только на основании отдельных тестов.

## 0.3.0 — Batch Reconciliation & Load Testing

### Производительность
- Для одиночного правила с обязательным совпадением reference и нулевым допуском по сумме добавлен индексированный поиск кандидатов по счёту, валюте, reference, сумме и диапазону дат.
- Убраны отдельные SQL-запросы поиска кандидатов для каждой строки этого сценария. Запись групп 1:1, участников и событий аудита выполняется партиями до 500 групп внутри одной транзакции PostgreSQL.
- Неоднозначные прямые и обратные совпадения остаются исключениями; при больших суммах сохраняется обязательное утверждение другим контролёром. Для нескольких правил или ненулевого допуска используется прежний универсальный алгоритм.

### Инструменты проверки
- Добавлен end-to-end benchmark HTTP preview/commit, повторного импорта, постановки задания, worker, итоговых финансовых инвариантов и закрытия периода.
- В обычном CI запускается небольшой синтетический E2E-сценарий, результат сохраняется как reconcilex-e2e-synthetic.
- Отдельный workflow_dispatch «Full Reconciliation Benchmark» допускает запуск профиля 80000 пар + 20000 дополнительных внутренних строк (всего 180000) и несколько независимых повторов.
- Добавлены проверки 620 однозначных групп, обратной неоднозначности, повторного задания, точных сумм и четырёх глаз для крупных групп.

### Ограничения
- Полный 180000-строчный прогон не считается прошедшим автоматически: он запускается вручную; его измерения нужно оценивать по фактическому отчёту на конкретном SHA.
- Быстрый путь пока применим только к одиночному правилу с reference=true и tolerance_minor=0. Полная промышленная нагрузочная, off-site и security приёмка остаются отдельными задачами.

## 0.2.0 — Reliability & Operations

### Добавлено
- Сервис ежедневного резервирования PostgreSQL 16 и S3-оригиналов с атомарной публикацией.
- SHA-256 манифест, 7 завершённых поколений по умолчанию, проверка свежести копии.
- Команды backup once, verify, restore-check и status. Проверяется архив во временной PostgreSQL БД с точными финансовыми инвариантами.
- Опциональный HTTPS reverse proxy с пользовательскими сертификатами, TRUSTED_HOSTS.
- Инструмент производительности для 80000 внешних и 100000 внутренних записей и отдельного preview 20000 строк. CI публикует JSON-артефакт сокращённого прогона.

### Исправлено
- Экранирование CSV-формул с ведущими пробелами и управляющими символами.
- Обработка повреждённых ZIP/XLSX как 422.
- Заголовок Retry-After для ограниченного входа (429).
- Конфликт повторного исходника, если источник совпадает, а тип/период загрузки отличается.

### Ограничения
Локальный архив не заменяет off-site копии. TLS требует правильных сертификатов, нагрузочный end-to-end прогон автосверки 180000 строк ещё не пройден, полнота production security не подтверждена. Источник статуса — docs/STATUS.md и GitHub Actions по точному SHA.
