# Матрица реализации PV-FIN-03

Инженерный статус версии 0.3.0. Проект содержит работающий backend и тесты, но не является сертифицированной платёжной системой. Полный акт приёмки PV-FIN-03 пока не подписан: для этого требуются нагрузочная и эксплуатационная проверки на документированном стенде.

## Реализованные требования

| ID | Что реализовано |
| --- | --- |
| FIN-F-01 | Версионируемые профили, карта колонок, кодировка, разделитель, формат дат, валюта источника |
| FIN-F-02 | Предпросмотр с суммой, числом валидных строк и локализованными по строке ошибками |
| FIN-F-03 | SHA-256 исходного файла плюс источник, естественный ключ строки и уникальные индексы |
| FIN-F-04 | Оригинал в SILO (S3-совместимое хранилище), сырой текст строки, normalized JSON, importBatchId |
| FIN-F-05 | Все финансовые суммы — целочисленные minor units; строгий Decimal при разборе |
| FIN-F-06 | Шесть воспроизводимых форматов, генератор 150000 строк и DB-seed CLI |
| FIN-F-07 | Приоритеты, версии, окна дат, tolerance_minor, сравниваемые признаки |
| FIN-F-08/09 | 1:1 только при единственном кандидате на максимальном приоритете; при равенстве — исключение |
| FIN-F-10 | Группы 1:n и n:1 до десяти строк на стороне множественности, одной валюты и счёта; ручное создание |
| FIN-F-11 | Частичный уникальный индекс только активного membership |
| FIN-F-12/13 | Версии правил, объяснение признаков, сохранение утверждённых групп при повторном задании |
| FIN-F-14 | Очередь unmatched, ambiguous, wrong_currency, amount_mismatch, duplicate; невалидные оригиналы сохраняются отдельно, без financial posting |
| FIN-F-15/16/17/18 | Автор и комментарий, независимый controller при превышении лимита, блокировки, версия группы, отмена через событие аудита |
| FIN-F-19 | Суммы и открытые исключения по источнику, валюте и счёту |
| FIN-F-20/21 | Snapshot + SHA-256 при закрытии, неизменяемая история версий; повтор отчёта из сохранённого snapshot |
| FIN-F-22 | CSV экспорт с проверкой SourceGrant |
| FIN-F-23 | График динамики причин расхождений — не реализован (Could) |

Установлены PostgreSQL-ограничения, миграции Alembic, JWT+Argon2id, пять ролей, серверная проверка источников, worker с устойчивой job-таблицей, 429 при повторных неверных логинах, структурированные логи HTTP, локальные p50/p95, исходные файлы в S3-совместимом хранилище, Docker Compose и CI.

## Что осталось до промышленной приёмки

1. Инструмент измерения preview 20000 строк и отдельных массивов 80000/100000 готов. Добавлен HTTP/worker/closure E2E-бенчмарк и отдельный ручной GitHub workflow для 80000 пар + 20000 дополнительных внутренних строк. Обычный CI выполняет уменьшенную проверку; фактический полный прогон 180000 и подтверждённый SLO ещё не выполнены. Issue #2 открыт.
2. CI выполняет E2E Docker Compose с PostgreSQL, SILO, API, worker и backup, включая restore-check во временную БД. Испытания сетевых аварий SILO/PostgreSQL и восстановления на другом сервере пока не выполнены.
3. Ежедневные снимки PostgreSQL и SILO, SHA-256, ротация и restore-check реализованы. Для production нужна отдельная зашифрованная off-site копия, проверки переноса на независимый сервер и мониторинг алертов.
4. TLS reverse proxy предложен как необязательный профиль Compose; реальные сертификаты, домен, сетевой доступ, хранилище секретов, отдельные рабочие аккаунты остаются настройками развёртывания.
5. Полное RBAC E2E на всех маршрутах и негативные тесты конкурентных сценариев при промышленных нагрузках.
6. Автоматическое 1:n/n:1 отсутствует сознательно: в текущей версии автоматическое сопоставление только 1:1; групповые решения создаёт оператор, что соответствует ручному сценарию комиссий.
7. Дополнительная проверка реконструкции всех закрытых цифр из архива оригиналов без доступа к исходным рабочим таблицам.

Никакие из этих пунктов не объявлены завершёнными только потому, что присутствуют отдельные endpoint, тестовые фикстуры или документация.

Документы v0.2.0: OPERATIONS.md, PERFORMANCE.md, SECURITY.md, CHANGELOG.md. Факт прохождения испытаний проверяйте по GitHub Actions на конкретном коммите, а не по наличию файлов.

## v0.3.0 — индексированный путь 1:1

В одном периоде и источнике при единственном замороженном правиле (require_reference=true, tolerance_minor=0) используется date-sorted индекс по account/currency/reference/amount и пакетная вставка group/member/audit/issue в одной транзакции. Проверяются симметричные кандидаты, лимиты окон дат, отсутствие пересечений membership, high-risk approval и точная разница в minor units. При нескольких правилах и ненулевом допуске используется существующий алгоритм, поэтому его производительность при 180000 строк требует отдельных оптимизаций. Числовые результаты относятся только к конкретным CI-артефактам, универсальный p95 не объявляется.
