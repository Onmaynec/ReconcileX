# Матрица реализации PV-FIN-03

Инженерный статус версии 0.7.0. Проект содержит работающий backend и тесты, но не является сертифицированной платёжной системой. Полный акт приёмки PV-FIN-03 пока не подписан: для этого требуются нагрузочная и эксплуатационная проверки на документированном стенде.

## Что осталось до промышленной приёмки

1. Инструмент измерения preview 20000 строк и отдельных массивов 80000/100000 готов. Добавлен HTTP/worker/closure E2E-бенчмарк и отдельный ручной GitHub workflow для 80000 пар + 20000 дополнительных внутренних строк; с v0.6.0 они умеют проверять ненулевой допуск и точную финансовую дельту. Обычный CI выполняет уменьшенную проверку; фактический полный прогон 180000 и подтверждённый SLO ещё не выполнены. Issue #2 открыт.
2. CI выполняет E2E Docker Compose с PostgreSQL, SILO, API, worker и backup, включая restore-check во временную БД. Испытания сетевых аварий SILO/PostgreSQL и восстановления на другом сервере пока не выполнены.
3. Добавлен opt-in репликатор завершённых PostgreSQL/SILO-снимков во внешний HTTPS S3 с SSE, HMAC-манифестами и проверкой обратного чтения. Реализован отказ от локальной ротации при недоступности внешнего сервиса, offsite-verify и offsite-drill во временную БД, а также healthcheck и опциональный HTTPS webhook. Реальная настройка Object Lock, независимый сервер, перенос на новый bucket и измеренные RPO/RTO ещё не подтверждены; Issue #6 открыт.
4. TLS reverse proxy предложен как необязательный профиль Compose; реальные сертификаты, домен, сетевой доступ, хранилище секретов, отдельные рабочие аккаунты остаются настройками развёртывания.
5. Добавлены негативные E2E проверки grant revoke, сессий, отключения пользователя, предотвращения пересекающихся периодов и source isolation при close/reopen. Полная RBAC-матрица всех маршрутов и испытания конкурентного доступа на промышленных объёмах пока не завершены; Issue #4 остаётся открытым.
6. Автоматическое 1:n/n:1 отсутствует сознательно: в текущей версии автоматическое сопоставление только 1:1; групповые решения создаёт оператор, что соответствует ручному сценарию комиссий.
7. Дополнительная проверка реконструкции всех закрытых цифр из архива оригиналов без доступа к исходным рабочим таблицам.

Никакие из этих пунктов не объявлены завершёнными только потому, что присутствуют отдельные endpoint, тестовые фикстуры или документация.

Документы v0.2.0: OPERATIONS.md, PERFORMANCE.md, SECURITY.md, CHANGELOG.md. Факт прохождения испытаний проверяйте по GitHub Actions на конкретном коммите, а не по наличию файлов.

## v0.3.0 — индексированный путь 1:1

В одном периоде и источнике при единственном замороженном правиле (require_reference=true, tolerance_minor=0) используется date-sorted индекс по account/currency/reference/amount и пакетная вставка group/member/audit/issue в одной транзакции. Проверяются симметричные кандидаты, лимиты окон дат, отсутствие пересечений membership, high-risk approval и точная разница в minor units. При нескольких правилах и ненулевом допуске используется существующий алгоритм, поэтому его производительность при 180000 строк требует отдельных оптимизаций. Числовые результаты относятся только к конкретным CI-артефактам, универсальный p95 не объявляется.

## v0.4.0 — контроль доступа и конкурентная целостность

- `User.token_epoch` (Alembic 0004) добавлен к проверяемым JWT, отзыв происходит после смены/сброса пароля либо отключения пользователя. Прежние JWT не обходят новую проверку.
- Реализованы административные disable/enable/reset-password/revoke-grant с записями в append-only audit. В аудит не попадают значения паролей.
- Worker под блокировкой проверяет текущую роль, enabled и SourceGrant; revoke/disable сериализуются с длительной финансовой транзакцией. Если отзыв состоялся до проверки, job заканчивается неуспешно без изменений финансовых записей.
- Закрытие и повторное открытие периода требуют прав контролёра на все фактически задействованные источники, включая отклонённые строки и замороженные правила заданий.
- Создание нового периода с перекрывающимся диапазоном защищено PostgreSQL advisory lock; два конкурирующих API-запроса не могут оба успешно создать пересекающиеся периоды.
- `tests/test_security_v040.py` проверяет изменения паролей, отзыв JWT/грантов, отключение учётной записи, исходники, роли, запрет чужого close/reopen, отказ worker и конкурентное создание периодов. В CI отдельно проверяется миграция старой схемы.

Полную промышленную приёмку, внешний TLS и управление секретами, многопользовательское нагрузочное испытание и аварийное восстановление на отдельном сервере эта версия не объявляет завершёнными.

Дополнительно реализованы и включены в регрессионные тесты `auth/logout-all`, безопасный список пользователей для admin и просмотр текущих SourceGrant. Эти методы не раскрывают хеши паролей и запрещены остальным ролям.

## v0.5.0 — Off-site Recovery

- `ops/offsite.py` реплицирует полный локальный архив в самостоятельный S3 по HTTPS с другими учётными данными. Используется серверное шифрование AES256 или AWS KMS, HMAC-SHA256 подпись манифеста отдельным секретом, SHA-256 каждого дампа и оригинала, проверка после чтения с удалённого хранилища.
- Манифест является последним условным PutObject с `If-None-Match`; незаконченная репликация не отображается как завершённая. Повтор отправки не перезаписывает существующие объекты, а проверяет их хеши.
- Сервис backup не выполняет локальную ротацию до успешной внешней передачи всех завершённых снимков. Для восстановления после сетевых отказов есть `offsite-sync`.
- `offsite-verify` проверяет все удалённые данные; `offsite-drill` скачивает внешний архив и проверяет его через временную PostgreSQL-БД. Проверка состояния и опциональный HTTPS webhook позволяют подключить внешний мониторинг.
- `compose.offsite.yaml` подключается явно, локальный сценарий без дополнительных переменных не изменён. CI проверяет конфигурацию, а `tests/test_offsite_v050.py` проверяет сетевые сбои, повтор, подмену манифеста и дампа, шифрование, скачивание без локальной копии, status и уведомления **с имитацией удалённого S3**.

Issue #6 остаётся открытым: подключение физически независимого сервера, настроенная у провайдера политика Object Lock, полное восстановление в отдельный S3 bucket, проверка сценария утраты основного хоста и измерение RPO/RTO не проведены. Отдельно не закрыты нагрузка #2 и промышленный security acceptance #4.

## v0.6.0 — Reconciliation Performance

- Индексированный 1:1-путь теперь применяется ко всем одиночным правилам с `require_reference=true` (включая `tolerance_minor>0`). Нулевая сумма расхождения выбирается по дате, ненулевая — через диапазон суммы в отсортированном индексе.
- Сохраняются двусторонняя проверка однозначности, валюты и счёта, окно дат, независимо согласуемые high-risk группы, immutable audit, атомарная запись по 500 и повторный запуск без дублей.
- В MatchGroup и audit сохраняется фактический `delta_minor`, рассчитанный целочисленно, а не округлённый float.
- Добавлены регрессии 620 пар с отклонениями по сумме, прямой и обратной неоднозначности, границ допуска/даты и независимого подтверждения крупной операции.
- CI выполняет отдельный сквозной сценарий точных и неточных групп, а ручной workflow допускает тестирование 180000 строк с произвольным `--tolerance-minor`.

**Ограничения:** полная проверка 180000 строк ещё не выполнена; многоправильный и безреференсный режимы переведены в v0.7.0 на индексированный поиск, но полномасштабное измерение производительности пока отсутствует. Issue #2 открыт; остальные требования #4/#6 также не закрыты.

## v0.7.0 — Multi-Rule Engine

- Все автоматические 1:1-сценарии (одиночные и несколько правил; `require_reference=true/false`; `tolerance_minor=0/>0`) используют один индексированный путь, не вызывающий отдельный SQL SELECT кандидатов на каждую исходную строку.
- Для каждого источника читаются только UUID, вид, счёт, валюта, reference, amount_minor и дата. Индексы по дате/сумме строятся для нужных форм правил, поиск ограничивает диапазон. Сортировка правил по приоритету и ключу сохранена.
- Проверяются уникальность в обе стороны, отказ от произвольного совпадения, high-risk согласование и фиксация фактической финансовой дельты. Все массовые изменения находятся в одной транзакции с batch insert по 500.
- Новые регрессии охватывают 621 пару и три приоритета, несколько правил одного приоритета, отсутствие reference, допуск и границы дат, активные membership, аудиторский след, повтор job и блокировки high-risk.
- Небольшой E2E сценарий с `--rules-mode priority-fallback` включён в CI. Полный workflow можно использовать для отдельных измерений в тестовой PostgreSQL.

**Не доказано:** полноценная нагрузочная приёмка 180000 записей, набор 150000 строк шести форматов, p50/p95 многопользовательских операций, целевой расход памяти и устойчивость при распределениях с большим числом одинаковых сумм. Issue #2 остаётся открытым. Независимый DR #6 и полная security acceptance #4 не закрыты.
