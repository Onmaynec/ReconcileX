# Сценарий замеров PV-FIN-03

Нагрузочные испытания не могут считаться выполненными без фактического замера на определённом компьютере. В v0.2.0 появился воспроизводимый инструмент, но не опубликовано универсальных обещаний о скорости.

Полный запуск (только синтетические данные):

~~~sh
python -m scripts.benchmark --external 80000 --internal 100000 --preview 20000 --trials 3 --output demo-output/performance.json
~~~

Создаются 80000 внешних и 100000 внутренних строк месяца и 20000 строк предпросмотра. Замеряются p50/p95 парсинга, точные суммы в minor units, пик памяти процесса, параметры CPU/RAM, версия Python и ОС. Порог p95 предпросмотра по умолчанию 120 секунд.

Для дополнительного измерения bulk insert в PostgreSQL:

~~~sh
python -m scripts.benchmark --external 80000 --internal 100000 --preview 20000 --trials 3 --db-load --output demo-output/performance-db.json
~~~

Флаг --db-load создаёт отдельные синтетические источник и период и проверяет итоговые суммы в DB. В целях безопасности запись без дополнительного разрешения допускается только в базу, имя которой включает _test. Это не тест для рабочей финансовой БД. Если пользователь явно устанавливает ALLOW_BENCHMARK_WRITES=1, он самостоятельно принимает риск добавления неснимаемых финансовых записей в выбранную среду.

CI выполняет уменьшенный прогон 1000+1250 строк c загрузкой в PostgreSQL и полноценный парсинг preview 20000 строк, сохраняет отчёт в JSON-артефакт reconcilex-perf-synthetic. Числа следует читать из GitHub Actions, а не из README.

В v0.3.0 для единственного reference-aware правила с точным совпадением суммы появился индексированный путь без отдельного SQL-запроса на каждый кандидат. Начиная с v0.6.0 этот быстрый путь также обслуживает одиночные reference-aware правила с ненулевым допуском по сумме. При нескольких правилах или отсутствии обязательного reference по-прежнему используется универсальный движок. Производительность полной сверки 180000 строк требует отдельного измерения: наличие быстрого пути не подтверждает достижение SLO. Измерения парсинга нельзя выдавать за p95 сквозного выполнения задачи.

Для закрытия Issue #2 нужен отдельный отчёт с SHA ревизии, CPU/RAM/диском, временем импорта, скоростью матчинга, долей ambiguous, нагрузкой от параллельных пользователей, E2E p50/p95 и результатами повторного запуска.

## E2E-сценарий v0.3.0

Скрипт scripts/e2e_benchmark.py создаёт только синтетические файлы, новый источник и период, выполняет HTTP preview/commit внешнего и внутреннего файлов, проверяет повторный импорт, запускает реальный DB worker, проверяет 1:1 группы, 2 активных участника на группу, суммы minor units, количество исключений, затем закрывает период через HTTP и сохраняет SHA-256 отчёта.

~~~sh
python -m scripts.e2e_benchmark --pairs 80000 --internal-extra 20000 --external-extra 0 --output demo-output/e2e-180k.json
python -m scripts.e2e_benchmark --pairs 1000 --internal-extra 250 --external-extra 100 --runs 3 --output demo-output/e2e-repeat.json
~~~

Первый сценарий создаёт 80000 внешних и 100000 внутренних записей за январь 2099, 80000 ожидаемых подтверждённых 1:1 групп, 160000 активных участников и 20000 несопоставленных внутренних строк. Второй сценарий дополнительно проверяет открытые исключения на внешних записях. Артефакт включает время HTTP preview, commit, повторного commit, обработки задания, закрытия и общую продолжительность, а также параметры машины и пиковую память процесса. Для 2–10 повторов выводятся p50/p95 времени reconcile, close и wall (один прогон недостаточен для этих процентилей).

**Защита от случайного запуска:** DATABASE_URL должна указывать на БД, название которой заканчивается _test. В противном случае запись запрещена без явного ALLOW_BENCHMARK_WRITES=1. Каждый запуск создаёт новые исходники, источники и закрытый период; выполняйте его только на одноразовом тестовом стенде с достаточным диском.

В GitHub Actions появился ручной workflow «Full Reconciliation Benchmark». Настройки по умолчанию: pairs=80000, internal_extra=20000, external_extra=0, runs=1. Доступен по Actions → Full Reconciliation Benchmark → Run workflow. В обычном Backend CI используется короткая проверка с 300 парами и 100 дополнительными записями; её JSON-артефакт называется reconcilex-e2e-synthetic.

**До закрытия Issue #2:** необходим фактический полный 180000-строчный прогон, отдельный тест 150000 строк шести форматов, проверка latency при нескольких одновременных операторах, нагрузки на диск и стабильности многоправильного алгоритма. Цифры короткого CI-прогона не переносятся на полный объём.

## Допуск по сумме и E2E-бенчмарк v0.6.0

В прежней версии ненулевой допуск по сумме вызывал универсальную сверку с отдельными SQL-запросами на каждый внешний платёж. Теперь индексированный путь по `(account,currency,reference)` сортирует кандидатов по `amount_minor`; `bisect_left/right` ограничивает область поиска окном `[amount-tolerance,amount+tolerance]`, после чего проверяется `day_window`. При `tolerance=0` используется датированный индекс по точной сумме. В обоих режимах выполняется обратный поиск и отклоняются многозначные 1:1-кандидаты.

Тест `test_tolerant_indexed_matching_keeps_exact_minor_unit_deltas` проверяет 620 пар, включая переход через пакет в 500, реальные знаковые `delta_minor`, сумму аудита, идемпотентность и отсутствие ложных исключений. Другие тесты проверяют неоднозначность forward/reverse, границы дат/сумм и high-risk approval.

В `scripts.e2e_benchmark` добавлены:
- `--tolerance-minor N`: разрешённое абсолютное отклонение в minor units для **одного** правила с обязательным reference (по умолчанию 0).
- `--drift-minor N`: одинаковое искусственное расхождение на каждой паре, 0 ≤ N ≤ min(tolerance, 999). Для внутреннего платежа сумма `1000-N`, для внешнего `1000`.
- В `results.verified.approved_delta_minor` подтверждается сумма дельт всех утверждённых групп; сверяются суммы по обеим сторонам, количество групп и активных участников. Выводятся `matcher_mode`, `tolerance_minor`, `drift_minor`.

~~~sh
python -m scripts.e2e_benchmark --pairs 250 --internal-extra 50 --external-extra 25 --tolerance-minor 5 --drift-minor 3 --output /tmp/reconcilex-tolerant-test.json
python -m scripts.e2e_benchmark --pairs 80000 --internal-extra 20000 --tolerance-minor 5 --drift-minor 3 --output demo-output/e2e-tolerant-180k.json
~~~

Первый сценарий выполняется автоматически в CI с 250 парами, 50 дополнительными внутренними и 25 внешними строками; JSON сохраняется в `reconcilex-e2e-tolerant-synthetic`. Второй — **только пример отдельного полного запуска** на подготовленном стенде. Его наличие в документации не означает, что он измерен или уложился в SLO.

В ручном workflow «Full Reconciliation Benchmark» есть входные значения `tolerance_minor` и `drift_minor`, по умолчанию оба равны 0 (режим exact). Значения времени и памяти зависят от CPU/RAM/диска, числа повторов, распределения reference и величины допуска. Высокая концентрация одинаковых reference и большой диапазон допуска увеличивают количество рассматриваемых кандидатов и способны ухудшить результат. Не переносите результаты быстрого одиночного правила на многоправильный движок. Issue #2 открыт до полного нагрузочного протокола.
