# Эксплуатация и восстановление ReconcileX v0.4.0

## Здоровье

- GET /health/live: HTTP-процесс отвечает.
- GET /health/ready: PostgreSQL доступен.
- docker compose ps, docker compose logs -f api worker backup: состояние и ошибки.
- docker compose run --rm backup status --max-age-hours 36: код 0 при наличии завершённой копии моложе 36 часов. Эту проверку использует Docker healthcheck.
- GET /api/v1/admin/metrics: p50/p95 по последним 10000 запросам на маршрут, только для admin и только в памяти текущего процесса.

## Автоматический бэкап

Сервис backup создаёт снимок сразу после старта и затем ежедневно в час BACKUP_HOUR_UTC (по умолчанию 03:00 UTC). Снимки сохраняются в отдельном backup_data volume; последние BACKUP_KEEP завершённых поколений хранятся по умолчанию в количестве 7.

Для ручной диагностики:

~~~sh
docker compose run --rm backup once
docker compose run --rm backup verify
docker compose run --rm backup restore-check
docker compose run --rm backup status --max-age-hours 36
~~~

Порядок резервирования: сначала pg_dump -Fc делает согласованный PostgreSQL-снимок, затем копируются все оригиналы S3. Этот порядок работает при инварианте неизменности объектов: приложение не перезаписывает и не удаляет оригиналы после записи, а их адреса содержат SHA-256. Администратор не должен удалять объекты во время резервирования.

В JSON-манифест включены размеры и SHA-256 дампа и каждого объекта. Архив становится видимым только после завершения и проверки хешей. Ротация удаляет только предыдущие завершённые архивы, а не текущий.

Команда restore-check создаёт новую случайно именованную PostgreSQL-БД, восстанавливает дамп без перезаписи рабочей базы, сверяет ссылки импортных пакетов на объекты, количество строк и суммы в minor units, проверяет SHA-256 исторических закрытий и удаляет временную БД. Для проверки необходимы права CREATE DATABASE. Автоматическое восстановление действующей базы отсутствует намеренно.

## Восстановление после аварии

Не запускайте pg_restore --clean на рабочей базе. Скопируйте полный архив на изолированную машину, поднимите PostgreSQL 16 и совместимое S3-хранилище, проверьте manifest, восстановите в новую БД и объекты в новый bucket, затем переключите API/worker после независимой сверки и согласования. Для проверки используйте restore-check с отдельным тестовым Postgres.

Текущий backup_data находится на том же хосте. Отказ диска или сервера уничтожит и его: настройте внешнюю зашифрованную копию с неизменяемым хранением и отдельными правами. Встроенного off-site копирования в версии 0.2.0 нет.

При успешном расписании теоретический RPO — до 24 часов плюс время резервирования. Если резервирование не состоялось, гарантии нет: системное наблюдение должно сигнализировать об unhealthy после 36 часов. RTO зависит от объёма и стенда; установленного измеренного RTO пока нет. restore-check выводит длительность операции duration_seconds для учёта на своём оборудовании.

## Обновление и расследование

Перед обновлением выполните once, verify и restore-check; проверьте, что сохранены оригиналы, и только после этого обновляйте Docker Compose. После обновления проверьте миграции, /health/ready, роли и финансовые отчёты закрытого периода.

HTTP 409 означает конфликт повторного файла/натурального ключа или блокировку закрытого периода. HTTP 422 означает неверный CSV/XLSX, значение, валюту или дату. HTTP 403 означает отказ роли/гранта; скачивание оригинала сопровождается событием аудита. Не редактируйте финансовые таблицы вручную. Повтор неудачного job после сбоя worker делается с проверкой идемпотентности.

Процедуры TLS и прав описаны в SECURITY.md; незавершённые эксплуатационные испытания — в STATUS.md.

## Обновление схемы на v0.4.0

Миграция `0004_session_epoch` добавляет `users.token_epoch` со значением 0. При обновлении существующей базы v0.3.0 миграция выполняется автоматически сервисом migrate в Docker Compose, но перед обновлением необходимо сделать `backup once` и `backup restore-check`. Ранее выданные JWT без `ver` необходимо получить заново посредством повторного входа. В результате смены пароля, административного сброса или отключения пользователя все ранее выданные JWT становятся недействительными.

Для восстановления административного доступа необходимо иметь хотя бы одну включённую учётную запись admin. Отзыв SourceGrant будет применён к новым запросам сразу после завершения операции, а worker сериализуется с отзывом, чтобы исключить финансовый commit после подтверждённого отзыва. Не изменяйте таблицу users или source_grants вручную — используйте API, чтобы сохранить аудит.
