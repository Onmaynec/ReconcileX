# Эксплуатация и восстановление ReconcileX v0.5.0

## Здоровье

- GET /health/live: HTTP-процесс отвечает.
- GET /health/ready: PostgreSQL доступен.
- docker compose ps, docker compose logs -f api worker backup: состояние и ошибки.
- docker compose run --rm backup status --max-age-hours 36: код 0 при наличии завершённой копии моложе 36 часов. Эту проверку использует Docker healthcheck.
- GET /api/v1/admin/metrics: p50/p95 по последним 10000 запросам на маршрут, только для admin и только в памяти текущего процесса.

## Автоматический бэкап

Сервис backup создаёт снимок сразу после старта и затем ежедневно в час BACKUP_HOUR_UTC (по умолчанию 03:00 UTC). Снимки сохраняются в отдельном backup_data volume; последние BACKUP_KEEP завершённых поколений хранятся по умолчанию в количестве 7.

Для ручной диагностики:

~~~sh
docker compose run --rm backup once
docker compose run --rm backup verify
docker compose run --rm backup restore-check
docker compose run --rm backup status --max-age-hours 36
~~~

Порядок резервирования: сначала pg_dump -Fc делает согласованный PostgreSQL-снимок, затем копируются все оригиналы S3. Этот порядок работает при инварианте неизменности объектов: приложение не перезаписывает и не удаляет оригиналы после записи, а их адреса содержат SHA-256. Администратор не должен удалять объекты во время резервирования.

В JSON-манифест включены размеры и SHA-256 дампа и каждого объекта. Архив становится видимым только после завершения и проверки хешей. Ротация удаляет только предыдущие завершённые архивы, а не текущий.

Команда restore-check создаёт новую случайно именованную PostgreSQL-БД, восстанавливает дамп без перезаписи рабочей базы, сверяет ссылки импортных пакетов на объекты, количество строк и суммы в minor units, проверяет SHA-256 исторических закрытий и удаляет временную БД. Для проверки необходимы права CREATE DATABASE. Автоматическое восстановление действующей базы отсутствует намеренно.

## Восстановление после аварии

Не запускайте pg_restore --clean на рабочей базе. Скопируйте полный архив на изолированную машину, поднимите PostgreSQL 16 и совместимое S3-хранилище, проверьте manifest, восстановите в новую БД и объекты в новый bucket, затем переключите API/worker после независимой сверки и согласования. Для проверки используйте restore-check с отдельным тестовым Postgres.

В базовом профиле backup_data остаётся на том же хосте. Для защиты от утраты машины используйте опциональный профиль compose.offsite.yaml (v0.5.0) и настоящий независимый S3-сервер. Одна только локальная копия не обеспечивает аварийное восстановление после потери хоста.

При успешном расписании теоретический RPO — до 24 часов плюс время резервирования. Если резервирование не состоялось, гарантии нет: системное наблюдение должно сигнализировать об unhealthy после 36 часов. RTO зависит от объёма и стенда; установленного измеренного RTO пока нет. restore-check выводит длительность операции duration_seconds для учёта на своём оборудовании.

## Обновление и расследование

Перед обновлением выполните once, verify и restore-check; проверьте, что сохранены оригиналы, и только после этого обновляйте Docker Compose. После обновления проверьте миграции, /health/ready, роли и финансовые отчёты закрытого периода.

HTTP 409 означает конфликт повторного файла/натурального ключа или блокировку закрытого периода. HTTP 422 означает неверный CSV/XLSX, значение, валюту или дату. HTTP 403 означает отказ роли/гранта; скачивание оригинала сопровождается событием аудита. Не редактируйте финансовые таблицы вручную. Повтор неудачного job после сбоя worker делается с проверкой идемпотентности.

Процедуры TLS и прав описаны в SECURITY.md; незавершённые эксплуатационные испытания — в STATUS.md.

## Обновление схемы на v0.4.0

Миграция `0004_session_epoch` добавляет `users.token_epoch` со значением 0. При обновлении существующей базы v0.3.0 миграция выполняется автоматически сервисом migrate в Docker Compose, но перед обновлением необходимо сделать `backup once` и `backup restore-check`. Ранее выданные JWT без `ver` необходимо получить заново посредством повторного входа. В результате смены пароля, административного сброса или отключения пользователя все ранее выданные JWT становятся недействительными.

Для восстановления административного доступа необходимо иметь хотя бы одну включённую учётную запись admin. Отзыв SourceGrant будет применён к новым запросам сразу после завершения операции, а worker сериализуется с отзывом, чтобы исключить финансовый commit после подтверждённого отзыва. Не изменяйте таблицу users или source_grants вручную — используйте API, чтобы сохранить аудит.

## v0.5.0 — Off-site Recovery

### Подготовка защищённого внешнего хранилища

1. Создайте **отдельный от основного SILO** S3 bucket на независимом сервисе с HTTPS. Включите versioning и Object Lock с retention не меньше согласованного срока хранения. Для основной копии выдайте ограниченные права PutObject/GetObject/ListBucket/HeadObject, **без DeleteObject**; этот клиент никогда не удаляет данные на внешнем S3.
2. Выдайте отдельные access key/secret key, отличающиеся от основных ключей SILO. Выберите SSE-S3 (AES256) или SSE-KMS (aws:kms с ключом `OFFSITE_S3_KMS_KEY_ID`). Проверьте, что провайдер поддерживает условный PutObject `If-None-Match: *` и возвращает режим шифрования через HeadObject. Без этих механизмов публикация **завершается ошибкой**, не объявляя результат успешным.
3. Создайте **независимый** `OFFSITE_MANIFEST_HMAC_KEY` длиной минимум 32 символа (лучше криптографически случайные 64 и более). Сохраните его отдельно от хоста и S3-паролей: этот ключ нужен и для проверки архивов после катастрофы. Не коммитьте его, не кладите в CI и не пересылайте через мессенджеры.
4. Укажите все обязательные `OFFSITE_S3_ENDPOINT`, `OFFSITE_S3_BUCKET`, `OFFSITE_S3_ACCESS_KEY`, `OFFSITE_S3_SECRET_KEY`, `OFFSITE_MANIFEST_HMAC_KEY` в защищённом `.env` на машине. Не копируйте секреты в исходники. Остальные переменные и примеры перечислены в `.env.example`.
5. Запустите `docker compose -f compose.yaml -f compose.offsite.yaml up --build -d`. Без этого дополнительного файла поведение остаётся локальным, а внешний S3 не используется.

### Управление

~~~sh
docker compose -f compose.yaml -f compose.offsite.yaml run --rm backup once
docker compose -f compose.yaml -f compose.offsite.yaml run --rm backup offsite-sync
docker compose -f compose.yaml -f compose.offsite.yaml run --rm backup offsite-verify
docker compose -f compose.yaml -f compose.offsite.yaml run --rm backup offsite-drill
docker compose -f compose.yaml -f compose.offsite.yaml run --rm backup status --max-age-hours 36
~~~

`offsite-sync` догружает все локальные завершённые снимки, включая те, отправка которых оборвалась. При повторе данные сверяются с уже сохранёнными объектами; существующие ключи не перезаписываются. `offsite-verify` скачивает и проверяет SHA-256 **каждого объекта** последней завершённой копии, а также подписанный HMAC манифеста. С `--remote-snapshot YYYYMMDDTHHMMSSZ-xxxxxxxx` можно выбрать конкретный архив для verify/drill.

`offsite-drill` берёт копию **из внешнего S3**, временно скачивает её в отдельный каталог внутри BACKUP_ROOT, запускает существующий `restore-check` в новой случайной PostgreSQL-БД и удаляет только собственный временный каталог. На рабочую БД и bucket оригиналов ничего не записывается. Команде нужны права на CREATE DATABASE и свободное место под полный архив. Для настоящего аварийного теста выполняйте этот сценарий на **независимом** сервере со своей пустой PostgreSQL, затем отдельно восстановите оригиналы в новый S3 bucket, сравните хеши и отчёты, измерьте RPO/RTO и задокументируйте результат.

**Нельзя считать локальный запуск offsite-drill испытанием потери хоста**. Встроенная проверка восстановления не переключает API на резервную площадку. Внешнее восстановление и измеренный RTO/RPO по-прежнему в Issue #6.

### Атомарность, ротация и наблюдение

У каждого архива есть уникальный идентификатор. PostgreSQL dump и копии оригиналов отправляются первыми, сверяются после обратного чтения; `manifest.json` с отдельным HMAC записывается только последним с условием `If-None-Match`. Незавершённая загрузка **не считается** завершённым снимком. Локальная ротация выполняется только после подтверждения всех локальных снимков во внешнем хранилище. Если сервис недоступен, новый локальный снимок сохраняется и старые не удаляются; `offsite-sync` можно повторить вручную.

При `OFFSITE_ENABLED=1` команда `status` проверяет, что **последний локальный** снимок есть удалённо, подпись HMAC совпадает и время создания не превышает `OFFSITE_MAX_AGE_HOURS` (по умолчанию 36 часов). При отсутствии/старении копии команда возвращает ненулевой код, а healthcheck контейнера переходит в unhealthy. Проверка статуса проверяет только манифест; периодически вызывайте также `offsite-verify` для полной проверки байтов.

Необязательная переменная `OFFSITE_ALERT_WEBHOOK_URL` задаёт HTTPS endpoint мониторинга: отправляются JSON-поля service, event, timestamp при ошибке регулярного backup или команды status. Финансовые суммы, файлы, имена пользователей, ключи и адрес webhook в запрос/логи не добавляются. Сбой доставки webhook отмечается отдельно в stderr; он **не** превращает ошибочную копию в успешную. Подключите внешний мониторинг событий, состояния Docker health и частоты алертов — сам webhook не гарантирует доставку без стороннего приёмника.

### Политика хранения и аварийный протокол

Локальная `BACKUP_KEEP` влияет только на volume, **не удаляет ничего во внешнем S3**. Длительность off-site retention настраивается у провайдера через bucket lifecycle/Object Lock: сервис ReconcileX не управляет блокировками, не подтверждает их активность и не удаляет удалённые архивы. Зафиксируйте независимые права, настройки lock, отдельную копию HMAC-ключа, частоту проверки, стоимость хранения, фактический RPO и длительность восстановления. Не используйте GitHub artifacts как хранилище резервных копий: там публикуются только синтетические отчёты тестов.
