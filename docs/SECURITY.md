# Безопасность ReconcileX v0.9.0

## HTTPS-подключение

В базовом Compose API доступен только на 127.0.0.1:8000, а PostgreSQL и SILO не публикуют порты наружу. Не открывайте API напрямую в интернет.

При наличии действительных сертификата и ключа вашего домена:

1. Сохраните fullchain.pem и privkey.pem в локальном каталоге certs/; каталог исключён из Git.
2. Установите в .env переменную TRUSTED_HOSTS с реальным доменом, например finance.example.com. Значение * запрещено.
3. Выполните docker compose -f compose.yaml -f compose.tls.yaml up --build -d.
4. Проверьте цепочку TLS, HTTPS healthcheck, локальную доступность API и firewall.
5. Настройте обновление сертификатов и внешнее безопасное хранилище секретов.

Шаблон находится в ops/nginx.conf. Он использует TLS 1.2/1.3, HSTS, ограничение тела запроса и перезаписывает ненадёжные forwarded-заголовки. Не запускайте proxy без сертификатов. Опциональная конфигурация — не гарантия production security.

## Данные, права и аудит

Пять ролей: operator, controller, admin, analyst, auditor. Исходные строки доступны только разрешённым ролям и SourceGrant. Аналитику доступны сводные отчёты, но не загрузка оригиналов и не сырой экспорт. Попытка получить исходный файл без прав фиксируется отдельным security-событием в audit.

Большие сверки утверждает отдельный контролёр. Запрет самоподтверждения действует даже при изменении роли автора.

Пароли хешируются Argon2id, JWT подписываются серверным секретом (не менее 32 символов). Эндпоинт входа использует PostgreSQL-счётчик неудачных попыток (пять за 60 секунд для username + адрес подключения), после чего отвечает 429 с Retry-After. При обратном прокси приложение видит IP прокси, а не IP конечного пользователя: для публичного доступа необходим дополнительный сетевой rate limiter.

CSV экспорт предотвращает исполнение формул в табличных процессорах, включая формулы с начальными пробелами и управляющими символами. Повреждённые XLSX/ZIP получают 422 вместо необработанной ошибки. HTTP-ответы имеют no-store, nosniff и no-referrer.

## Незавершённые элементы

Нужны production-секрет-менеджер, MFA/SSO по требованиям окружения, реальное сетевое ограничение запросов, негативные E2E тесты всех маршрутов и независимое тестирование аварийных сценариев. Смотрите Issue #4 и STATUS.md.

## Отзыв сессий и управление аккаунтами (v0.4.0)

JWT включает claim `ver` и подписывается как ранее HS256. При каждом запросе сервер загружает текущего пользователя из PostgreSQL, проверяет enabled и точное совпадение `ver` с `users.token_epoch`. Если версия изменилась, запрос возвращает HTTP 401.

- `POST /api/v1/auth/change-password`: `{"current_password":"...","new_password":"..."}`. Требуется текущий пароль; все прежние JWT отзываются.
- `POST /api/v1/admin/users/{id}/reset-password`: `{"new_password":"..."}`. Требуется admin, новый секрет не выводится в audit.
- `POST /api/v1/admin/users/{id}/disable`: admin, блокировка новых запросов и повышение token_epoch.
- `POST /api/v1/admin/users/{id}/enable`: admin; прежние токены остаются недействительными, нужно войти заново.
- `POST /api/v1/admin/grants/revoke`: `{"user_id":"UUID","source_id":"UUID"}`. Требуется admin; операция идемпотентна, audit создаётся при фактическом отзыве.

Нельзя отключить собственную административную учётную запись. При отключении администраторов используется согласованный порядок блокировок и проверка, что останется хотя бы один активный admin.

### Согласованность отзыва при работе worker

Перед финансовой сверкой worker блокирует строку учётной записи и выданные ему SourceGrant до окончания транзакции. Если администратор отозвал разрешение раньше, worker не подтверждает ни одной пары. Если worker уже начал операцию, запрос отзыва ждёт окончания этой транзакции: окончание административного запроса означает, что раньше начатая транзакция уже завершена. Ошибка job фиксируется с состоянием failed. Для снятия блокировки задания в ошибке нужно заново выдать право и явно повторить задачу.

### Периоды и аудит

Оператор и контролёр не имеют глобального права на все финансовые источники: close/reopen проверяет Batch, Record, MatchGroup, ReconcileIssue и rules_snapshot всех заданий в периоде. История закрытий продолжает фильтроваться по SourceGrant. Запрещённые попытки загрузки оригиналов пишутся в отдельный append-only audit.

### Ограничения

Миграция не заменяет управление секретами и TLS. Новые JWT выдаются только после подтверждения нового пароля, а для распределённой авторизации обязателен доступ к PostgreSQL. Внешнее TLS-развёртывание, MFA, центральное хранилище секретов, сетевой rate limiter и полный формальный RBAC-аудит остаются за рамками этой версии.

### Самостоятельный выход и инспекция прав

`POST /api/v1/auth/logout-all` инвалидирует все уже выпущенные JWT данного аккаунта; после этого требуется повторный логин.

`GET /api/v1/admin/users?limit=100&offset=0` возвращает только id, username, роль и статус enabled. Хеши паролей и детали сессий не раскрываются. `GET /api/v1/admin/grants?user_id=UUID` показывает список действующих SourceGrant конкретного пользователя. Для обоих методов обязательна роль admin.

## Off-site архивы (v0.5.0)

Бэкапы содержат исходные финансовые файлы и потенциально персональные данные. Не передавайте их через GitHub, почту или незащищённые публичные ссылки. Opt-in профиль требует отдельный HTTPS S3 endpoint, иные access/secret ключи, шифрование SSE-AES256 или SSE-KMS и независимый HMAC-ключ длиной минимум 32 символа. При несовпадении HMAC манифест отвергается даже если SHA-256 был подменён. Неотмеченные как завершённые снимки не считаются восстановимыми. Секрет HMAC и ключ KMS необходимо резервировать в отдельном защищённом месте.

Защиту от административного удаления обеспечивает **политика облачного провайдера**, а не Python-код: включите Object Lock, versioning, независимые права без DeleteObject, контроль доступа к ключу шифрования и правила retention. Приложение не доказывает существование такой политики и не может гарантировать физическую изоляцию указанного endpoint. Включить конфигурацию может только администратор развёртывания. Webhook отправляет только имя события и дату, не содержимое архива. Реальное DR-испытание остаётся открытым.

## Доверенный reverse proxy и ограничение входа (v0.8.0)

Приложение не доверяет X-Forwarded-For или X-Real-IP само по себе. Для определения адреса клиента используется TCP peer. Только если peer принадлежит одному из явно настроенных TRUSTED_PROXY_CIDRS, приложение принимает одиночный валидный IP из X-Real-IP. Если proxy не доверен, заголовок отсутствует или некорректен, используется адрес peer. Список CIDR при ошибочном синтаксисе отклоняется с конфигурационной ошибкой, а не расширяет доверие.

TLS Compose закрепляет Nginx за статическим адресом TLS_PROXY_IP внутри BACKEND_SUBNET. TRUSTED_PROXY_CIDRS по умолчанию содержит только этот адрес с маской /32. Nginx полностью перезаписывает X-Real-IP и X-Forwarded-For значением $remote_addr; переданный клиентом адрес не переносится к API. Если меняется subnet, все три параметра необходимо обновить согласованно. Не добавляйте в trusted CIDR весь диапазон Docker-сети: доверять следует только reverse proxy.

На /api/v1/auth/token Nginx применяет независимое ограничение по IP (5 запросов в минуту, burst 2, без задержки). Превышение лимита возвращает 429 до приложения. Дополнительно сохраняется DB-backed счётчик неудачных попыток на пару username + доверенный client IP: пять ошибок в 60-секундном окне. В локальном профиле без TLS proxy forwarded headers не используются.

Nginx также добавляет X-Frame-Options: DENY и ограничивает ненужные браузерные возможности через Permissions-Policy; server_tokens отключён. TLS 1.2/1.3, HSTS, nosniff и no-referrer сохранены. CI использует только временный self-signed сертификат и синтетические несуществующие логины; это проверка конфигурации и поведения, не тест доверенной цепочки сертификатов реального домена.

### Настройка .env

В .env.example приведены согласованные значения:

~~~dotenv
BACKEND_SUBNET=172.29.240.0/24
TLS_PROXY_IP=172.29.240.10
TRUSTED_PROXY_CIDRS=172.29.240.10/32
~~~

Если выбранная подсеть уже занята Docker или локальной сетью, выберите свободную подсеть и адрес proxy внутри неё. Укажите ровно этот адрес в TRUSTED_PROXY_CIDRS. Убедитесь, что адрес не используется другим контейнером. После изменения сетевой конфигурации пересоздайте Compose network и сервисы в согласованном окне обслуживания.

### Проверки v0.8.0

- Unit-тесты проверяют прямой spoofing, доверенный и недоверенный peer, неверный forwarded IP и некорректную конфигурацию CIDR.
- Контрактный тест проверяет обязательную аутентификацию всех API-маршрутов, кроме выдачи токена.
- Admin inspection endpoints проверяются для всех неадминистративных ролей.
- CI создаёт временный TLS-сертификат, поднимает Nginx, проверяет HTTPS health и security headers, затем отправляет серию запросов с поддельным X-Real-IP и проверяет HTTP 429.

### Что не закрыто

Issue #4 остаётся открытым. Не реализованы MFA/SSO и подключение конкретного внешнего secret manager; полная RBAC-матрица каждого действия, конкурентные тесты на целевой нагрузке и независимый security review требуют отдельной приёмки. TLS smoke не заменяет проверку реального сертификата, DNS, firewall, обновления и хранения private key.


## File-backed secrets (v0.9.0)

Для развёртывания без передачи секретов в Compose environment используйте отдельный файл:

~~~sh
docker compose -f compose.yaml -f compose.secrets.yaml up --build -d
~~~

До запуска создайте на хосте отдельные файлы с секретами и укажите в .env только пути:

~~~dotenv
DB_PASSWORD_FILE=./secrets/db_password
JWT_SECRET_FILE=./secrets/jwt_secret
S3_ACCESS_KEY_FILE=./secrets/s3_access_key
S3_SECRET_KEY_FILE=./secrets/s3_secret_key
~~~

Внутри контейнеров файлы монтируются в /run/secrets. PostgreSQL читает пароль через POSTGRES_PASSWORD_FILE, SILO — через MINIO_ROOT_USER_FILE и MINIO_ROOT_PASSWORD_FILE; API и worker используют общий загрузчик NAME_FILE. Для off-site архива можно добавить compose.offsite.secrets.yaml и задать пути OFFSITE_S3_ACCESS_KEY_FILE, OFFSITE_S3_SECRET_KEY_FILE, OFFSITE_MANIFEST_HMAC_KEY_FILE.

Загрузчик отклоняет одновременное задание непустой переменной и соответствующего _FILE, нечитаемые/слишком большие файлы, некорректный UTF-8 и NUL. Секреты не включаются в диагностические сообщения. Пароль БД при сборке DATABASE_URL кодируется как URI-компонент, поэтому @, :, / и другие специальные символы не меняют структуру подключения.

### Границы защиты

Compose file-backed secrets для локального Docker Compose — это read-only mount из файлов хоста, а не внешний secret manager и не шифрование файлов на диске. Ограничьте права к каталогу (например, доступ только deployment user), не добавляйте его в Git и не помещайте содержимое секретов в логи или CI artifacts. Для production используйте штатный секретный менеджер платформы или безопасную инъекцию файлов, организуйте ротацию и отдельное резервирование ключей. При смене DB password обновите и файл PostgreSQL, и файл приложения, затем пересоздайте сервисы в согласованном окне.

Off-site credentials и HMAC-ключ должны быть отдельными от основных S3 credentials. Для них используйте дополнительный secrets override. Не применяйте CI тестовые значения в реальной среде.

### RBAC приёмка v0.9.0

tests/test_security_v090.py проверяет доступ пяти ролей к отчётам, строкам, исключениям, экспорту, профилям, правилам, истории и метрикам. Отдельно проверяются admin-only изменения, операторские и контролёрские операции, права submitter на job и аудит отказов при скачивании оригиналов. Тесты используют синтетические записи и не заменяют независимый security review.

### Что остаётся открытым

Issue #4 остаётся открытым: нет MFA/SSO, внешнего Vault/KMS integration, полного review всех бизнес-операций независимой стороной, реальных production-сертификатов/домена и security acceptance на целевом стенде. File-backed secrets закрывает передачу секретов через Compose environment для соответствующего профиля, но не решает хранение/ротацию на хосте.
